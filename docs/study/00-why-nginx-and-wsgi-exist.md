# nginx 와 WSGI 는 왜 생겼나

> 작성 2026-09-05. `01-nginx-uwsgi-flask.md` 가 "무엇을 하는가" 라면, 이 문서는
> **"왜 그렇게 생겼는가"** 다. 지금의 구조는 설계된 게 아니라 30년에 걸쳐
> 문제를 하나씩 맞고 자란 결과다. 배경을 알면 각 레이어의 경계가 자의적으로
> 보이지 않는다.

---

## 0. 두 갈래의 역사

nginx 와 WSGI 는 **서로 관련 없는 두 개의 문제**에서 따로 태어났다. 흔히 한
덩어리로 배우지만 원인이 다르다.

```
문제 A: "요청 하나에 프로세스 하나" 가 감당이 안 된다   →  nginx  (2004)
문제 B: "프레임워크마다 서버 붙이는 법이 다르다"        →  WSGI   (2003)
```

A 는 **성능/확장성** 문제고 B 는 **인터페이스/호환성** 문제다. 둘이 나중에
만나서 지금의 `nginx → uWSGI → Flask` 가 됐다.

---

## 1. 문제 B 의 역사: 파이썬을 웹에 붙이는 법

### 1.1 CGI (1993) — 요청마다 프로그램을 새로 실행한다

최초의 동적 웹 방식. 이름이 오해를 부르는데, **CGI 는 프로그램도 라이브러리도
아니고 "규약"** 이다. "웹서버가 외부 프로그램을 실행할 때 정보를 이렇게 주고받자"
는 합의문 한 장.

#### 실제로 어떻게 생겼나

`hello.cgi` 파일 하나를 두면 그게 곧 웹 앱이었다.

```python
#!/usr/bin/env python3
import os
print("Content-Type: text/plain")   # 헤더
print()                              # 빈 줄 = 헤더 끝 (HTTP 규칙)
print("Hello,", os.environ.get("QUERY_STRING"))
```

`GET /cgi-bin/hello.cgi?name=daeyoung` 이 오면 웹서버가:

```
1. fork() + exec("/usr/lib/cgi-bin/hello.cgi")   ← 프로세스를 새로 만든다
2. 환경변수를 채워서 넘긴다
     REQUEST_METHOD=GET
     QUERY_STRING=name=daeyoung
     PATH_INFO=/cgi-bin/hello.cgi
     CONTENT_LENGTH=0
     SERVER_NAME=...
3. POST 바디는 그 프로세스의 stdin 으로 흘려준다
4. 그 프로세스의 stdout 을 그대로 HTTP 응답으로 쓴다
5. 프로세스가 끝난다. 죽는다.
```

**입력 = 환경변수 + stdin, 출력 = stdout.** 유닉스 명령줄 프로그램 그대로다.
그래서 언어를 안 가렸다 — Perl, C, 셸 스크립트 아무거나 stdout 에 글자만 뱉으면
웹 앱이 됐다. 이 단순함이 1990년대 웹을 폭발시켰다.

#### 왜 죽었나

```
요청 1개 = fork + exec + 파이썬 인터프리터 기동 + import + DB 커넥션 생성
         → 앱 로직   0.001초
         → 오버헤드  0.05초
```

근본 문제는 속도 자체가 아니라 **요청과 프로세스 수명이 1:1 로 묶였다**는 것이다.
상태를 아무것도 들고 있을 수 없다. DB 커넥션 풀? 다음 요청이면 프로세스가 없으니
무의미. 인메모리 캐시? 마찬가지.

#### CGI 는 사실 안 죽었다 — 이름을 바꿔 살아 있다

이 절이 이 문서에서 제일 실용적인 부분이다.

**① 여러분 Flask 앱 안에 있다.** `request.environ` 을 찍어 보면
`REQUEST_METHOD`, `QUERY_STRING`, `PATH_INFO` 같은 **대문자 키**가 나온다.
WSGI 가 CGI 환경변수 이름을 그대로 물려받았기 때문이다. 30년 된 규약의 화석이
지금 돌고 있다.

**② FastCGI (1996) → php-fpm → uwsgi 프로토콜.** FastCGI 는 CGI 에서
"프로세스를 죽이지 말고 상주시키자" 하나만 고친 버전이다. PHP 의 `php-fpm` 이
바로 이것이고(FPM = **F**astCGI **P**rocess **M**anager), **uWSGI 의 `uwsgi`
프로토콜도 같은 계보의 사촌**이다. `uwsgi_pass` 가 `proxy_pass` 보다 빠른 이유가
여기 있다 — HTTP 를 다시 파싱하지 않고 이미 파싱된 필드를 바이너리로 넘긴다.

**③ 서버리스.** AWS Lambda 의 실행 모델은 개념적으로 CGI 로의 회귀다. 요청이
오면 프로세스를 띄우고 끝나면 죽인다. 콜드 스타트 문제도 CGI 가 겪던 바로 그
문제고, "하드웨어가 충분히 빨라졌고 기동을 최적화할 수 있다" 는 전제로 30년 만에
같은 아이디어가 돌아온 셈이다.

### 1.2 mod_python / mod_perl (1996~2000) — 인터프리터를 서버 안에 넣는다

해법은 명확했다. **매번 띄우지 말고, 웹서버 프로세스 안에 인터프리터를 상주시키자.**
Apache 모듈로 구현됐고 실제로 훨씬 빨랐다.

그런데 새 문제가 생겼다.

```
Zope    → mod_python 용 어댑터를 따로 만든다
Django  → mod_python 용 어댑터를 따로 만든다
CherryPy→ 자체 서버를 내장한다
web.py  → 또 다른 방식
```

프레임워크가 **Apache 에 묶였다.** 다른 서버로 옮기려면 어댑터를 새로 짜야 했다.
프레임워크 M개 × 서버 N개 = **M×N 개의 어댑터**를 세상이 유지해야 하는 구조다.
게다가 mod_python 은 API 가 Apache 내부에 밀착돼 있어서 이식이 사실상 불가능했다.

### 1.3 WSGI (PEP 333, 2003) — 가운데에 규격을 하나 박는다

Phillip J. Eby 가 2003년 12월에 제안했다. 아이디어는 소프트웨어 공학의 고전이다.

```
   [M×N]                          [M+N]

Django ──┬── Apache          Django ─┐            ┌─ Apache
Zope   ──┼── nginx           Zope   ─┼─ WSGI 규격 ─┼─ nginx
Flask  ──┴── IIS             Flask  ─┘            └─ uWSGI
 (모든 조합에 어댑터)          (각자 규격 한쪽만 구현)
```

Java 진영의 Servlet API 에서 영감을 받았고 규격은 의도적으로 **극단적으로 작게**
잡았다. "환경 dict 와 콜백을 받아 바이트열 iterable 을 반환하는 호출 가능 객체."
그게 전부다. 라우팅도, 템플릿도, 세션도 규격에 없다 — 전부 프레임워크의 일이다.

```python
def application(environ, start_response):
    start_response("200 OK", [("Content-Type", "text/plain")])
    return [b"hello"]
```

이 작음이 성공의 이유였다. 구현하기 쉬우니 모두가 구현했다. 2010년 파이썬 3용으로
문자열/바이트 구분을 정리한 **PEP 3333** 이 나왔고 그게 현행이다.

> **★ 요점** — WSGI 는 성능을 위한 물건이 **아니다.** 순전히 **결합도를 끊기 위한
> 규격**이다. 여러분이 Flask 로 짠 앱을 uWSGI, Gunicorn, mod_wsgi, Waitress 중
> 아무 데나 올릴 수 있는 이유이자, 그 선택이 앱 코드를 한 줄도 바꾸지 않는 이유.

### 1.4 그래서 uWSGI (2009)

WSGI 규격은 "앱이 어떻게 생겼는지" 만 정한다. **그 앱을 실제로 띄우고, 프로세스를
관리하고, 죽으면 살리는 프로그램**은 별도로 필요하다. 그게 애플리케이션 서버고
이탈리아 Unbit 의 Roberto De Ioris 가 2009년에 만든 uWSGI 가 그중 하나다.

같은 자리의 다른 선택지: Gunicorn(2010, 파이썬 구현, 설정이 단순), mod_wsgi
(Apache 내장), Waitress(순수 파이썬, Windows 가능). uWSGI 는 C 로 짜였고 기능이
압도적으로 많다 — 그리고 그만큼 설정 옵션이 수백 개라 악명도 높다.

## 2. 문제 A 의 역사: C10K

이건 파이썬과 아무 상관이 없는, 웹서버 자체의 문제다.

### 2.1 Apache 의 모델: 커넥션 하나에 프로세스/스레드 하나

1995년 Apache 가 나왔을 때는 이게 합리적이었다. 동시 접속자가 수십 명이었으니까.

```
접속 1000개 → 프로세스 1000개
             → 프로세스당 RSS 2~10MB (모듈 다 얹으면 더)
             → 2~10 GB RAM
             → 컨텍스트 스위칭으로 커널이 CPU 를 다 태운다
```

메모리보다 먼저 스케줄러가 죽는다. 프로세스 1000개를 번갈아 깨우는 비용이
실제 일보다 커지는 지점이 온다.

### 2.2 Dan Kegel, "The C10K problem" (1999)

**"장비 한 대가 동시 접속 1만 개를 감당하려면?"** 이라는 유명한 글이다. 당시
하드웨어로도 1만 커넥션의 **데이터 처리량 자체는** 충분히 감당됐다. 문제는
소프트웨어 모델이었다.

핵심 관찰: **웹 커넥션은 대부분의 시간을 아무것도 안 하고 있다.**

```
느린 회선의 사용자 1명, 30초짜리 요청:
  실제 CPU 사용    ≈ 0.01초
  나머지 29.99초   = 네트워크 대기
```

그런데 프로세스 모델은 그 29.99초 동안에도 프로세스를 통째로 잡아 둔다.
**커넥션 수와 프로세스 수를 1:1 로 묶은 것**이 잘못된 설계였던 것이다.

### 2.3 해법: 이벤트 루프 + epoll/kqueue

```
[프로세스 모델]                   [이벤트 모델]
커넥션마다 프로세스               프로세스 1개 (또는 코어당 1개)
  → 대기 = 프로세스가 잠듦          → "준비된 소켓 있냐" 를 커널에 물어본다
  → 1만 커넥션 = 1만 프로세스       → 준비된 것만 처리하고 즉시 다음
                                    → 1만 커넥션 = 소켓 1만 + 프로세스 몇 개
```

이 모델은 커널이 "많은 소켓 중 준비된 것" 을 **싸게** 알려줘야 성립한다.
기존 `select()`/`poll()` 은 매번 전체 목록을 훑어서 O(n) 이었다 — 1만 개면
매 루프마다 1만 번 검사다. FreeBSD 의 **kqueue**(2000)와 Linux 2.6 의
**epoll**(2003)이 이걸 O(1) 로 만들면서 비로소 실용화됐다.

**즉 nginx 는 커널 API 가 준비되자마자 등장한 것이지, 우연이 아니다.**

### 2.4 nginx (2004)

Igor Sysoev 가 러시아 포털 Rambler 의 트래픽을 감당하려고 2002년부터 만들었고
2004년 10월에 공개했다. 처음부터 C10K 를 겨냥한 이벤트 기반 설계였다.
(같은 동기로 나온 lighttpd 가 2003년에 먼저 있었다.)

nginx 는 애초에 **동적 콘텐츠를 만들 생각이 없었다.** 파이썬도 PHP 도 안 돈다.
대신 잘하는 게 셋이다: 정적 파일 서빙, 커넥션 관리, 그리고 **다른 놈에게 넘기기**.
그 "넘기기" 가 리버스 프록시이자 로드밸런서다.

## 3. 두 갈래가 만난다

여기서 지금의 구조가 나온다. 각자 자기가 잘하는 것만 하도록 역할을 쪼갠 것이다.

```
        느린 커넥션 1만 개                    파이썬 실행
        ────────────────                    ──────────
        이벤트 모델이 압승                   프로세스 모델이 필수
        (대기가 대부분)                      (GIL, 그리고 앱 코드는
                                              동기 blocking 스타일)
             ↓                                    ↓
          nginx  ────────────────────────────▶ uWSGI ──▶ Flask
       "싼 자원으로 대기를 흡수"           "비싼 자원을 짧게만 쓴다"
```

nginx 가 30초짜리 느린 업로드를 **버퍼에 다 받아 놓고** uWSGI 에 0.05초만에
넘기는 그 동작이, 두 모델의 장점을 이어붙인 결과물이다. 이걸
**buffering reverse proxy** 패턴이라고 부르고, 파이썬만의 얘기가 아니다 —
Ruby(Unicorn), PHP(php-fpm) 도 똑같은 이유로 똑같은 구조를 쓴다.

> **★ 요점** — 레이어가 세 개인 건 과잉설계가 아니라, **비용 구조가 다른 두 종류의
> 대기를 분리한 것**이다. 커넥션 대기는 싸게(nginx), 코드 실행은 비싸게(uWSGI).

## 4. Apache 는 대체되었나

**짧은 답: 부분적으로만. 그리고 Apache 는 1995년에 멈춰 있지 않다.**

### 4.1 Apache 가 한 일

1995년 등장. 그전까지 웹서버라 할 만한 것은 NCSA HTTPd 정도였고 관리자가 없어
방치돼 있었다. Apache 는 그 패치 묶음("**a patchy** server" 라는 농담 어원)에서
시작해 **"웹서버" 라는 물건 자체를 표준화**했다.

진짜 혁신은 **모듈 아키텍처**였다.

```
mod_ssl        HTTPS
mod_rewrite    URL 재작성 (정규식 기반. 지금도 강력하다)
mod_auth_*     인증
mod_php        PHP 인터프리터를 서버 프로세스 안에 내장
mod_python     파이썬 인터프리터 내장
mod_wsgi       WSGI 앱 구동
```

`mod_php` 가 특히 중요하다. **PHP 가 세상을 먹은 이유의 절반이 이것**이다 —
파일을 디렉토리에 던져 놓으면 그냥 돌았다. 별도 프로세스도, 소켓도, 설정도 없이.

그리고 **`.htaccess`**. 디렉토리마다 설정 파일을 두면 서버 재시작 없이 적용된다.
공유 호스팅 업체가 고객마다 격리된 설정을 줄 수 있었던 유일한 방법이었고, 그래서
웹호스팅 시장 전체가 Apache 위에 세워졌다.

### 4.2 nginx 는 대체가 아니라 분업이다

```
            Apache 혼자 다 하던 시절 (2000년대 초)
[클라이언트] ──▶ Apache ──┬─ 정적 파일
                         ├─ TLS
                         ├─ 커넥션 관리
                         └─ mod_php 로 앱 실행
                              ↑ 커넥션마다 프로세스 하나

                      지금
[클라이언트] ──▶ nginx ──────────────▶ php-fpm / uWSGI / Node
               커넥션·TLS·정적파일        앱 실행만
               (이벤트 모델)              (프로세스 모델)
```

**nginx 가 Apache 를 대체한 게 아니라, Apache 가 하던 일이 둘로 쪼개졌다.**
커넥션 관리는 이벤트 모델이 압도적으로 유리하고 앱 실행은 프로세스 모델이
필수인데, 이 둘을 한 프로그램이 다 하는 게 애초에 무리였던 것이다. 3절의
buffering reverse proxy 가 바로 그 분업의 이름이다.

### 4.3 Apache 도 가만있지 않았다

흔히 빠지는 함정. Apache 2.4(2012)의 **event MPM** 은 이벤트 기반이다.

| MPM | 모델 | 비고 |
|---|---|---|
| `prefork` | 커넥션당 프로세스 | 옛날 그것. `mod_php` 가 이걸 요구한다 |
| `worker` | 커넥션당 스레드 | 메모리는 나아짐 |
| **`event`** | **keep-alive 커넥션을 이벤트로** | **2.4 기본값. nginx 와 유사** |

그래서 "Apache = 느림" 은 2012년 이후로는 정확한 말이 아니다. 다만 `mod_php` 를
쓰면 `prefork` 로 되돌아가야 해서 현대적 배치는 Apache 에서도
`event MPM + php-fpm` 을 쓴다 — **결국 nginx 와 같은 구조로 수렴했다.**

### 4.4 점유율과 선택 기준

대략 nginx ~33%, Apache ~26% 수준이고 Cloudflare·LiteSpeed 등이 나머지를 나눈다
(집계 기관마다 편차가 크다). **Apache 는 죽지 않았다.** 다만 신규 프로젝트가
nginx 를 기본으로 고르는 경향이 뚜렷하고 Apache 는 기존 자산과 공유 호스팅에
두껍게 남아 있다.

| 상황 | 선택 |
|---|---|
| 리버스 프록시 / 로드밸런서 | **nginx** (또는 HAProxy, Envoy) |
| 정적 파일 대량 서빙 | **nginx** |
| 동시 접속이 아주 많음 | **nginx** |
| `.htaccess` 로 디렉토리별 설정이 필요 | **Apache** (nginx 는 이 기능이 아예 없다) |
| 레거시 `mod_*` 자산이 두꺼움 | **Apache** |
| 복잡한 `mod_rewrite` 규칙이 이미 있음 | **Apache** (nginx 로 옮기려면 다시 써야 한다) |

> **★ nginx 에 `.htaccess` 가 없는 건 미구현이 아니라 거부다.**
> 디렉토리별 설정 파일을 지원하려면 요청마다 경로를 거슬러 올라가며 파일 존재를
> 확인해야 한다 (`/a/b/c/` 요청 → `/a/b/c/.htaccess`, `/a/b/.htaccess`,
> `/a/.htaccess` 를 전부 stat). 요청당 디스크 I/O 가 여러 번 생기는 구조라,
> C10K 를 목표로 설계된 서버가 받아들일 수 없는 비용이었다.
> **nginx 의 성능은 상당 부분 "안 하기로 한 것들" 에서 나온다.**
>
> 실무적 함의: nginx 스택에서 설정 변경은 항상 중앙 conf 파일 +
> `nginx -s reload` 다. Apache 감각으로 앱 디렉토리에 설정 파일을 두는 방식은
> 통하지 않는다. 대신 설정이 한 곳에만 있어서 "이 동작이 어디서 나왔나" 추적이
> 훨씬 쉽다.

## 5. 그 뒤: ASGI 와 지금

WSGI 에는 태생적 한계가 있다. **요청 하나 = 함수 호출 하나 = 반환하면 끝** 이라
WebSocket, Server-Sent Events, HTTP/2 push, 그리고 `async def` 를 표현할 수 없다.

그래서 2016년경 **ASGI** 가 나왔다. WSGI 의 async 후계로, 서버는 Uvicorn/Hypercorn,
프레임워크는 FastAPI/Starlette/Django(3.0+) 가 쓴다.

**그럼 우리 스택은 낡았나?** 아니다. 갈리는 기준은 이렇다.

| | WSGI (Flask + uWSGI) | ASGI (FastAPI + Uvicorn) |
|---|---|---|
| 요청·응답 API | 완벽히 충분 | 충분 |
| WebSocket / SSE 스트리밍 | 불가능하거나 어색 | 네이티브 |
| 아웃바운드 대기가 긴 프록시 | 워커/스레드를 잡아먹는다 | 코루틴이라 훨씬 쌈 |
| 디버깅 난이도 | 낮음 (동기 스택트레이스) | async 함정이 많음 |

이 저장소에 실제로 걸리는 항목이 있다. `service_template.py` 는 upstream 응답을
**끝까지 버퍼링한 뒤 반환**한다 (`_proxy_request`). LLM 응답이 60초 걸리면 그
60초 동안 uWSGI 워커/스레드가 하나 묶인다. 토큰 스트리밍을 그대로 흘려보내려면
ASGI 가 훨씬 자연스럽다.

다만 지금 구조를 고를 이유도 명확하다. **버퍼링 프록시는 로직이 단순하고,
동시 사용자가 팀 규모(수~수십)면 워커 몇 개로 충분하다.** 사내 표준이 uWSGI 인
것도 이유고. 바꿀 만한 시점은 "동시 요청이 워커 수를 넘기 시작할 때" 이지,
"ASGI 가 최신이라서" 가 아니다.

## 7. 한 줄 요약

- **CGI** 는 "환경변수+stdin 으로 받아 stdout 으로 답한다" 는 규약이다. 매 요청마다
  프로세스를 만들어서 느렸고 → 인터프리터를 상주시켰다. 죽지 않고 이름만 바뀌어
  FastCGI·php-fpm·uwsgi 프로토콜로, 그리고 `request.environ` 의 대문자 키로 남아 있다.
- **상주시켰더니 프레임워크가 서버에 묶였다** → WSGI 라는 얇은 규격으로 끊었다.
- **커넥션마다 프로세스를 쓰니 1만 접속을 못 버텼다** (C10K) → nginx 가 이벤트 모델로 풀었다.
- **둘을 합쳐** 커넥션 대기는 nginx 가 싸게, 코드 실행은 uWSGI 가 비싸게 맡는 지금 구조가 됐다.
- **Apache 는 대체된 게 아니라 분업당했다.** 지금도 4분의 1쯤 돌고 있고,
  event MPM(2012) 이후로는 느리지도 않다. `.htaccess` 가 필요하면 여전히 Apache 다.
