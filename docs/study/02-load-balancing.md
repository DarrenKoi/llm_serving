## 0. 로드밸런싱은 두 군데에서 벌어진다

같은 단어를 쓰지만 완전히 다른 두 층이 있다. 이 구분이 안 되면 대화가 계속 어긋난다.

```
                     ┌── ① 인바운드 밸런싱 ──┐
[클라이언트] ──▶ nginx ──┬──▶ 앱서버 A          │  nginx / uWSGI 가 해준다
                        └──▶ 앱서버 B          │  코드 0줄
                     └───────────────────────┘
                                │
                     ┌── ② 아웃바운드 밸런싱 ─┐
                     └─▶ requests.post(...)   │  아무도 안 해준다
                          ├──▶ vLLM :8006     │  직접 짜거나
                          └──▶ vLLM :8007     │  nginx 를 하나 더 세워야
                     └───────────────────────┘
```

**uWSGI 의 `processes = 4` 는 ① 이지 ② 가 아니다.** 워커를 늘려도 나가는 목적지는
코드에 박힌 문자열 그대로다. "프로세스를 늘렸는데 왜 안 빨라지지" 의 대부분이 이 혼동이다.

## 1. 무엇을 얻으려고 하는가

로드밸런서를 세우는 이유는 넷인데, 서로 독립이다. **내가 넷 중 무엇을 원하는지**
부터 정하지 않으면 알고리즘 선택이 무의미해진다.

| 목적 | 설명 | 인스턴스 1개로도 되나 |
|---|---|---|
| **처리량 (throughput)** | 초당 더 많은 요청 | 안 됨. 대수를 늘려야 |
| **가용성 (availability)** | 하나 죽어도 서비스 유지 | 안 됨 |
| **지연시간 (latency)** | 요청 하나가 더 빨리 끝남 | **밸런싱으로는 안 됨** ← 흔한 오해 |
| **무중단 배포** | 하나씩 빼서 교체 | 안 됨 |

세 번째를 특히 조심해야 한다. 밸런싱은 **줄 서는 시간(queueing delay)** 만 줄인다.
서버가 놀고 있는 상태라면 요청 하나의 처리 시간은 인스턴스가 몇 개든 똑같다.
지연시간을 진짜로 줄이려면 모델을 줄이거나 병렬화(TP)를 하거나 하드웨어를 바꿔야 한다.

## 2. 알고리즘

### 2.1 Round Robin — 순서대로 한 번씩

```
요청 1 → A,  요청 2 → B,  요청 3 → A,  요청 4 → B
```

nginx 기본값. **모든 요청의 처리 비용이 비슷할 때만** 옳다.

깨지는 경우:

```
A: [========== 60초짜리 요청 ==========]
   ↑ 그런데 라운드로빈은 순서만 보므로
A: [====60초====][0.1초][0.1초]   ← 계속 A 에 꽂는다. A 는 큐가 쌓임
B:              [0.1초][0.1초]   ← B 는 절반만 받고 논다
```

### 2.2 Least Connections — 지금 제일 한가한 놈에게

```nginx
upstream pool { least_conn; server a:8006; server b:8007; }
```

활성 커넥션 수가 가장 적은 백엔드를 고른다. **처리 시간이 들쭉날쭉할 때**
라운드로빈보다 압도적으로 낫다. 60초짜리를 물고 있는 A 는 커넥션이 1이므로
다음 요청이 B 로 간다.

### 2.3 IP Hash / Consistent Hash — 같은 키는 항상 같은 곳으로

```nginx
upstream pool { hash $arg_session_id consistent; ... }
```

세션 어피니티(sticky session)가 필요할 때. 캐시 지역성을 살릴 때도 쓴다.
`consistent` 를 붙이면 백엔드가 하나 늘거나 줄 때 **전체가 아니라 1/N 만**
재배치된다 (consistent hashing). 안 붙이면 서버 대수가 바뀌는 순간 모든 키의
행선지가 뒤집힌다.

### 2.4 Weighted — 장비 성능이 다를 때

```nginx
server a:8006 weight=3;   # H200
server b:8007 weight=1;   # A100
```

### 2.5 정리

| 알고리즘 | 언제 |
|---|---|
| round robin | 요청 비용이 균일. 기본값 |
| **least_conn** | **처리 시간이 들쭉날쭉. LLM 은 여기** |
| hash / ip_hash | 세션 어피니티나 캐시 지역성이 필요 |
| weight | 백엔드 성능이 다름 |

## 3. 알고리즘보다 중요한 것: 헬스체크

**로드밸런서의 진짜 가치는 분배가 아니라 "죽은 놈을 빼는 것"** 이다. 분배만
필요하면 랜덤으로도 대충 되지만 죽은 백엔드를 계속 때리면 서비스가 반쯤 죽는다.

```nginx
upstream pool {
    least_conn;
    server 127.0.0.1:8006 max_fails=3 fail_timeout=30s;
    server 127.0.0.1:8007 max_fails=3 fail_timeout=30s;
}
```

- **passive (수동)**: nginx OSS 기본. 실제 요청이 `max_fails` 번 실패하면
  `fail_timeout` 동안 풀에서 뺀다. 공짜지만 **실패한 요청 몇 개는 사용자가 맞는다.**
- **active (능동)**: 주기적으로 헬스 엔드포인트를 찔러 본다. 사용자가 맞기 전에
  뺀다. nginx 는 상용판(Plus) 기능이고 OSS 는 HAProxy 나 Envoy 를 쓰면 된다.

### 왜 Flask 에서 직접 짜면 안 되는가

여기가 `01` 문서의 "워커는 상태를 공유하지 않는다" 와 만나는 지점이다.

```python
# 안티패턴
_dead_until = {}                       # ← 워커마다 별개의 dict
_counter = itertools.count()           # ← 워커마다 별개의 카운터
```

uWSGI 워커가 4개면 이 상태가 4벌이다. 워커 1이 "8007 은 죽었다" 를 학습해도
워커 2,3,4 는 계속 8007 을 때린다. 라운드로빈도 각자 0,1,0,1 을 돌아서 분배가
편향된다. 제대로 하려면 Redis 같은 공유 저장소가 필요하고 **그 순간
nginx `upstream` 블록 5줄보다 훨씬 무거워진다.**

> **★ 요점 — 아웃바운드 밸런싱이 필요해지면, 코드를 짜지 말고 nginx 를 하나 더 세워라.**
> 상태(누가 살아있나, 다음 차례가 누구인가)를 **프로세스 밖의 한 곳**에
> 두는 것이 핵심이고, nginx 는 그 상태를 이미 갖고 있다.

## 4. LLM 서빙에서 달라지는 점

여기서부터 일반 웹의 통념이 깨진다. 세 가지가 다르다.

### 4.1 요청 비용이 수백 배 차이 난다

일반 웹 API 는 대개 10~200ms 안에 끝난다. LLM 은 이렇다.

```
"안녕"                → 20 토큰 생성  → 0.5초
장문 요약 + reasoning → 4000 토큰     → 90초
```

**180배 차이.** 라운드로빈이 무너지는 교과서적 조건이다. `least_conn` 이
사실상 유일한 합리적 선택이다. (진짜 정답은 "대기 중인 토큰 수" 기준인데,
nginx 는 그걸 모른다. 활성 커넥션 수가 그나마 쓸 만한 근사다.)

### 4.2 서버가 이미 배칭을 하고 있다

vLLM 은 **continuous batching** 을 한다. 요청을 수백 개 동시에 물고 매 디코딩
스텝마다 배치를 재구성해서 GPU 를 채운다.

```
일반 웹서버:  요청 하나 처리 → 다음 요청     (밸런싱이 처리량을 늘린다)
vLLM:        요청 200개를 한 배치에 섞어 처리 (이미 안에서 병렬)
```

그래서 **인스턴스를 늘리기 전에 물어야 할 질문**이 있다.

```bash
# vLLM 로그에서
Running: 3 reqs, Pending: 0 reqs   ← Pending 이 0 이면 밸런싱해도 아무것도 안 변한다
Running: 64 reqs, Pending: 41 reqs ← 이제야 인스턴스를 늘릴 근거가 생긴다
```

`nvidia-smi` 의 GPU util 과 함께 본다. **util 이 낮고 Pending 이 0 이면 병목은
서버가 아니라 트래픽이다.** 이 상태에서 인스턴스를 늘리는 건 순수한 낭비다.

### 4.3 prefix cache 가 밸런싱과 충돌한다

이게 LLM 밸런싱의 가장 반직관적인 부분이다.

vLLM 은 **automatic prefix caching** 으로, 같은 접두사를 가진 요청의 KV 캐시를
재사용한다. 팀 전체가 같은 시스템 프롬프트를 쓴다면 그 부분의 prefill 이 통째로
생략된다 — 수천 토큰짜리 프롬프트면 엄청난 절약이다.

그런데 요청을 두 인스턴스로 흩뿌리면:

```
[인스턴스 1] 시스템프롬프트 KV 캐시 (자기 몫)
[인스턴스 2] 시스템프롬프트 KV 캐시 (똑같은 걸 또)
   → 캐시 히트율 하락, 메모리 중복, prefill 재계산
```

**밸런싱으로 번 처리량을 캐시 미스로 도로 뱉을 수 있다.** 그래서 LLM 전용
라우터(vLLM 의 router, Envoy AI Gateway 등)는 단순 least_conn 이 아니라
**prefix-aware routing** — 같은 접두사는 같은 인스턴스로 — 을 한다.

nginx 로 흉내 내려면 세션/사용자 키로 `hash ... consistent` 를 걸어 어피니티를
주는 정도가 현실적이다. 완벽하진 않지만 캐시 파편화를 크게 줄인다.

## 5. 이 저장소에 적용한다면

`flask_api/vlm_serve/service_template.py` 의 `upstream_base_url` 은 환경변수
`VLM_SERVE_<PREFIX>_BASE_URL` 을 먼저 본다. **이 한 줄이 확장 지점이다.**

```nginx
# 아웃바운드 전용 nginx (인바운드용과 같은 nginx 프로세스여도 된다)
upstream qwen_pool {
    least_conn;
    server 127.0.0.1:8006 max_fails=3 fail_timeout=30s;
    server 127.0.0.1:8007 max_fails=3 fail_timeout=30s;
}
server {
    listen 8106;
    location / {
        proxy_pass http://qwen_pool;
        proxy_read_timeout 900s;    # LLM 응답은 길다. 기본 60초면 504
        proxy_buffering off;        # 스트리밍을 쓴다면 필수
    }
}
```

```bash
# site.env — Flask 코드는 한 줄도 안 바뀐다
VLM_SERVE_QWEN3_8_27B_BASE_URL=http://127.0.0.1:8106
```

> **여담 — 여기 잠재 버그가 있었다 (2026-09-05 수정).** `env_prefix` 가
> `-` 만 `_` 로 바꾸고 **점(`.`)은 놔뒀다.** 슬러그 `qwen3.8-27b` 는
> `QWEN3.8_27B` 가 되고 환경변수 이름에 점은 쓸 수 없으니 위 override 가
> **조용히 무시**됐다. `mai-ui` 는 점이 없어 잘 동작했기 때문에 드러나지 않았다.
> 게다가 같은 로직이 `service_template.py` 와 `__init__.py` 에 **두 벌** 있었고
> 한쪽만 점을 처리하고 있어서, 프록시가 나가는 주소와 health 가 보고하는 주소가
> 갈릴 수 있었다. 지금은 `env_prefix_for()` 한 함수로 합쳤고
> `tests/test_vlm_serve.py` 가 둘이 일치하는지 검사한다.
>
> 교훈이 이 문서 주제와 맞닿아 있다: **같은 값을 두 곳에서 계산하면 언젠가
> 갈린다.** 3절에서 "밸런싱 상태를 코드가 아니라 nginx 한 곳에 두라" 고 한 것과
> 정확히 같은 이유다.

### 그런데 이 저장소에서는 아마 하면 안 된다

호스트 RAM 이 16GB, 스왑 없음, 웜 상태 여유가 ~4GB 다. 27B 두 번째 인스턴스는:

- 웨이트 로딩과 CUDA 그래프 캡처가 각각 RSS 피크를 만든다.
  `start_all.py` 가 모델을 **굳이 하나씩 순차 기동**하는 이유가 그거다.
- 이건 TP=2 를 2026-09-04 에 접었던 것과 **정확히 같은 벽**이다.
  GPU 메모리(282GB)가 아니라 호스트 RAM 이 먼저 한계에 닿는다.

**따라서 순서는 이렇다.** ① Pending 큐를 먼저 측정한다 → ② 0 이 아니면
`gpu_memory_utilization` / `max_num_seqs` 같은 단일 인스턴스 knob 부터 조정한다
(`08-serving-knobs-concepts.md`) → ③ 그래도 모자라면 그때 호스트 RAM 증설과
2번째 인스턴스를 함께 논의한다.

## 6. 한 줄 요약

- 밸런싱은 **처리량·가용성**을 주지, **지연시간은 안 준다.**
- 인바운드는 nginx/uWSGI 가 공짜로 해준다. **아웃바운드는 직접 세워야 한다.**
- 알고리즘은 `least_conn` 이 기본값보다 거의 항상 낫다 — 특히 LLM 처럼 처리
  시간이 들쭉날쭉하면.
- 진짜 가치는 분배가 아니라 **헬스체크**다. 그래서 Flask 코드가 아니라 nginx 다
  (워커는 상태를 공유하지 않는다).
- LLM 은 예외가 많다: 이미 continuous batching 중이고, **prefix cache 를
  깨뜨릴 수 있다.** 늘리기 전에 Pending 큐부터 재라.
