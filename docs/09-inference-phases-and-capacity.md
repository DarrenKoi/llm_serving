# Inference Phases And Capacity: Prefill / Decode / TTFT / 멀티유저

> 작성 2026-09-04. LLM 추론이 왜 **두 국면**으로 갈리는지, 그 둘의 병목이 왜 다른지,
> 그리고 그 차이가 **몇 명이 같이 쓸 수 있나**로 어떻게 이어지는지를 설명한다.
> 설정 knob 자체의 의미는 [`08-serving-knobs-concepts.md`](./08-serving-knobs-concepts.md),
> 실제 값은 `deploy_vlms/config/` 가 정본이다.

---

## 1. Prefill: 프롬프트를 한 번에 삼키는 국면

### 하는 일

요청이 도착하면 모델은 먼저 **프롬프트 전체**를 읽는다. 이때 두 가지가 만들어진다.

1. 모든 입력 토큰의 **KV cache** (뒤에 올 decode 가 참조할 재료)
2. **첫 번째 출력 토큰**

```
프롬프트: "다음 코드의 버그를 찾아줘: def foo(): ..."  (20,000 토큰)
   ↓ prefill — 20,000개를 한 번에 처리
KV cache 20,000 토큰분 채워짐 + 첫 토큰 "이" 출력
```

### 왜 한 번에 되나

핵심은 **프롬프트는 이미 전부 알고 있다**는 것이다. 5,000번째 토큰을 처리하려고
4,999번째 결과를 기다릴 필요가 없다. 전부 GPU 에 밀어넣고 행렬 하나로 처리한다.
`n`개 토큰이 `n`번의 순차 단계가 아니라 **한 번의 큰 병렬 연산**이 된다.

이게 decode 와 갈리는 결정적 차이다.

### 왜 compute 바운드인가

토큰이 수만 개면 GPU 연산 유닛이 포화된다. 메모리에서 가중치를 한 번 읽어오면
그 가중치로 **수만 토큰분의 곱셈**을 하므로, 병목이 메모리가 아니라 연산 능력이다.

비용은 두 항의 합이다.

```
prefill 비용 ≈ [선형항] 2 × 파라미터수 × n     ← n에 비례
             + [attention항] n² 관련 항         ← n의 제곱에 비례
```

`qwen3.8-27b` (27B, H200 1장) 대략치:

| 프롬프트 길이 | 선형항 | attention항 | **TTFT 대략** |
|---|---|---|---|
| 20,000 | ~2s | 무시 가능 | **~2s** |
| 262,144 | ~30s | ~20s | **~50s** |
| 1,010,000 | ~2min | ~5min | **5-10min** |

길이가 3.85배(262k → 1.01M)일 때 attention항이 **14.8배**로 뛰는 게 보인다.
`n²` 이라 그렇다. 짧은 프롬프트에서는 선형항이 지배하고 길어지면 attention항이
역전한다.

> `qwen3.8-27b` 는 64개 층 중 16개만 full attention 이라 저 `n²` 항이 평범한 dense
> 모델의 **1/4** 이다. 위 표의 값은 그 할인이 이미 적용된 결과다.

### chunked prefill

100만 토큰을 정말로 한 번에 넣으면 중간 activation 이 GPU 를 터뜨린다. 그래서
`MAX_NUM_BATCHED_TOKENS` 크기로 쪼개서 넣는다.

```
MAX_NUM_BATCHED_TOKENS=16384 일 때
  1,010,000 토큰 → 62 라운드로 나눠 prefill
```

키우면 prefill 이 빨라지지만 activation 메모리를 더 쓴다. 이미지 1장(1920x1080)이
~1300-2600 토큰이므로 16384 는 한 청크에 넉넉히 들어간다.

이 값의 또 다른 역할이 있다. 짧은 요청이 긴 prefill 뒤에 갇히지 않게 **끼어들 틈**을
만든다 - 청크 사이사이에 다른 요청의 decode 스텝이 들어갈 수 있다.

## 2. Decode: 토큰을 하나씩 뽑는 국면

### 하는 일

첫 토큰이 나온 뒤부터는 **자기회귀(autoregressive)** 다. 방금 만든 토큰을 다시
입력에 붙여 다음 토큰을 만든다. 앞 토큰이 정해져야 다음이 정해지므로 **병렬화가
원리적으로 불가능**하다.

```
"이"  →  "이 함수"  →  "이 함수는"  →  "이 함수는 None"  →  ...
        각 화살표가 별개의 forward pass. 순서를 못 건너뛴다.
```

### 왜 bandwidth 바운드인가

토큰 **하나**를 만들려고 27B 파라미터 **전부**를 HBM 에서 읽는다. 연산량은
토큰 1개분이라 우습게 적은데 읽어야 할 바이트는 그대로다. 그래서 연산 유닛은
놀고 메모리 버스만 바쁘다.

```
BF16 가중치 48GiB ≈ 51.5GB
H200 대역폭 4.8TB/s
→ 스텝당 최소 ~10.7ms → 이론 최대 ~93 tok/s (단일 스트림)
```

### 길이가 늘면 decode 도 느려진다

가중치만 읽는 게 아니다. attention 은 **앞의 모든 토큰의 KV** 를 매 스텝 읽는다.

```
스텝당 읽기 = 가중치(51.5GB) + 컨텍스트 길이 × 32KiB
```

| 컨텍스트 | KV 읽기 | 가중치 읽기 | 어느 쪽이 큰가 |
|---|---|---|---|
| 20,000 | 0.66GB | 51.5GB | 가중치 압도 |
| 200,000 | 6.6GB | 51.5GB | 가중치 우세 |
| 1,600,000 (8명×200k) | 52.4GB | 51.5GB | **KV 가 역전** |

긴 컨텍스트의 숨은 비용이 이것이다. TTFT 만 느려지는 게 아니라 **생성 속도 자체**가
느려진다.

---

## 3. 두 국면 대조

| | **Prefill** | **Decode** |
|---|---|---|
| 처리 단위 | 프롬프트 전체를 한 번에 | 토큰 하나씩 |
| 병렬화 | 가능 (다 알고 있으므로) | **불가능** (자기회귀) |
| 병목 | **compute** | **메모리 대역폭** |
| 비용을 정하는 것 | 입력 길이 (n, n²) | 모델 크기 + 컨텍스트 길이 |
| 지표 | **TTFT** | **TPOT** / tokens/sec |
| batching 효과 | **거의 없음** (5절) | **매우 큼** (5절) |
| 듣는 knob | `MAX_NUM_BATCHED_TOKENS`, prefix cache | 가중치 정밀도, 추측 디코딩 |

## 4. 지연 지표 읽는 법

```
요청 도착
  ├─ [큐 대기]       슬롯이 없으면 여기서 기다림 (TTFT에 포함된다)
  ├─ [Prefill]
  │   ↑───────── TTFT (Time To First Token) ─────────↑
  ├─ 첫 토큰
  ├─ [Decode] × 출력 토큰 수
  │   토큰 간격 = ITL (Inter-Token Latency) ≈ TPOT
  └─ 완료
```

```
E2E 응답 시간 = TTFT + (출력 토큰 수 × TPOT)
```

| 지표 | 정식 명칭 | 사용자 체감 |
|---|---|---|
| **TTFT** | Time To First Token | "언제 반응하나" |
| **TPOT** | Time Per Output Token | "얼마나 술술 나오나" |
| ITL | Inter-Token Latency | 사실상 TPOT 과 같은 값 |
| E2E | End-to-End latency | 전체 대기시간 |

**둘은 완전히 다른 레버로 움직인다.** 가중치를 FP8 로 내리면 TPOT 이 2배 빨라지지만
TTFT 는 거의 그대로다. 반대로 프롬프트를 절반으로 줄이면 TTFT 는 확 주는데 TPOT 은
안 변한다. "느리다"는 말이 나왔을 때 **어느 쪽이 느린지부터 갈라야** 엉뚱한 knob 을
만지지 않는다.

**TTFT 에 큐 대기가 포함된다는 점**도 기억할 것. 요청이 몰려 slot 을 못 잡으면
prefill 이 시작조차 못 하는데, 이건 모델이 느린 게 아니라 스케줄링 지연이라
레버가 또 다르다 (`MAX_NUM_SEQS`).

## 5. 왜 batching 은 decode 만 돕는가

멀티유저 용량 산정의 **전부**가 여기서 나온다.

### Decode: 가중치를 배치당 한 번만 읽는다

8명이 각각 토큰을 만들 때, 51.5GB 짜리 가중치 읽기는 **한 번**이면 된다.
읽어온 김에 8명분을 같이 계산하기 때문이다.

```
1명:  가중치 51.5GB  +  KV 1.6GB   = 53.1GB  →  스텝당 ~11ms
8명:  가중치 51.5GB  +  KV 13.1GB  = 64.6GB  →  스텝당 ~13.5ms
      (컨텍스트 50k 기준, 이론치)

일은 8배인데 시간은 1.2배.
```

멀티유저가 생각보다 잘 되는 이유가 전적으로 이것이다.

### Prefill: 나눠지지 않는다

반면 prefill 은 이미 GPU 를 포화시키고 있다. 8명분 prefill 은 그냥 8배 걸린다.

```
8명이 동시에 200k 프롬프트를 새로 던지면
  40초 × 8 = 마지막 사람은 5분 뒤에 첫 글자를 본다
```

**결론: 동시 사용자 수는 decode 가 아니라 prefill 이 정한다.**
그리고 그 prefill 을 지워주는 장치가 다음 절이다.

## 6. Prefix cache: prefill 을 반복하지 않게 하는 장치

vLLM V1 은 KV 블록을 프롬프트 prefix 로 해싱해 캐싱한다(기본 on). 대화 2턴째는
**바뀐 꼬리만** prefill 하고 앞부분은 캐시 히트다.

```
턴 1:  [시스템 프롬프트 + 파일 3개 + 질문]  120k 토큰 prefill  → ~20초
턴 2:  [········ 위와 동일 ········ + 답변 + 새 질문]
                 캐시 히트                    2k만 prefill → ~0.3초
```

사실상 **TTFT 최적화 장치**다. 코딩 에이전트나 반복 grounding 호출이 실용적인 것은
거의 전적으로 이 기능 덕분이다.

**트레이드오프:** 캐시된 prefix 는 **KV pool 을 그대로 쓴다.** 별도 공간이 아니다.

```
71GiB pool 기준
  대화당 200k (6.4GiB)  → ~11개 대화 캐시 유지
  대화당 262k (8GiB)    → ~8개
  대화당 1M  (30.8GiB)  → ~2개
```

즉 `MAX_MODEL_LEN` 을 늘리면 **캐시 보존 개수가 준다 = 2턴째 TTFT 가 나빠진다.**
인터랙티브 용도에서는 거의 항상 손해다. 여유를 쓰고 싶으면 길이가 아니라
`GPU_MEMORY_UTILIZATION` 을 올려 pool 자체를 키우는 편이 낫다.

## 7. 용량 산정: H200 1장으로 8명이 되나

`qwen3.8-27b` (GPU 1 단독 점유, KV pool ~71GiB, fp8 KV 32KiB/token) 기준.

### 7.1 `MAX_NUM_SEQS=8` 은 "8명" 이 아니다

8은 **동시에 생성 중인 시퀀스** 상한이지 사용자 수가 아니다. 사람은 응답을 읽고
생각하고 타이핑하는 동안 GPU 를 전혀 안 쓴다. 코딩 세션의 duty cycle 은 보통
10% 안팎이라 8슬롯으로 **동시 접속 20-40명**도 감당한다.

9번째 요청이 와도 에러가 아니라 **큐에 들어갈 뿐**이고 대기시간이 TTFT 에 더해진다.

### 7.2 메모리: 8명은 넉넉하다

KV pool 71GiB ÷ 32KiB = **총 2.32M 토큰** 수용.

| 시나리오 | 총 토큰 | KV 소요 | 판정 |
|---|---|---|---|
| 8명 × 200k (현실적 코딩 세션) | 1.6M | 49GiB | 여유 |
| 8명 × 262k (전원 꽉 채움) | 2.1M | 64GiB | 들어감 (여유 7GiB) |
| 16명 × 262k | 4.2M | 134GiB | **초과** → preempt 발생 |

### 7.3 처리량: 전 구간에서 읽는 속도보다 빠르다

H200 대역폭 4.8TB/s, 실효율 65% 가정한 **대략치**(실측 아님):

| 상황 | 스텝당 읽기 | 1인당 속도 |
|---|---|---|
| 1명, 50k 컨텍스트 | 53GB | ~59 tok/s |
| **8명, 50k 컨텍스트** | 65GB | **~48 tok/s** |
| **8명, 200k 컨텍스트** | 104GB | **~30 tok/s** |
| 8명, 262k 꽉 채움 | 120GB | ~26 tok/s |

사람이 읽는 속도가 5-10 tok/s 이므로 전 구간에서 여유가 있다.
200k 구간에서 느려지는 것은 5절에서 본 대로 **KV 읽기가 가중치를 역전**하기 때문이다.

### 7.4 갈리는 지점은 사용 패턴이다

| 패턴 | 결과 |
|---|---|
| 8명이 각자 **이어서 코딩** (prefix cache 히트) | 턴마다 꼬리만 prefill → **문제없음** |
| 8명이 **동시에** 새 200k 문서를 붙여넣음 | 40초 × 8 → **마지막 사람 5분 대기** |

### 7.5 먼저 터지는 곳은 GPU 가 아니다

**호스트 RAM 16GB, swap 없음.** 8개 동시 요청이 각각 body + token id 를 호스트에
얹는다. GPU 1 은 단독이라 여유롭지만 호스트는 `mai-ui` / `paddleocr` 와 공유고
OOM killer 는 원인 프로세스를 골라 죽이지 않는다 - **qwen 이 밀어붙여도 죽는 것은
production 루프일 수 있다.**

8명을 붙이기 전에 warm 상태에서 한 번 확인할 것:

```bash
uv run python deploy_vlms/scripts/check_host_ram.py
```

## 8. 무엇을 측정할 것인가

위 숫자는 전부 대역폭 나눗셈이지 벤치 결과가 아니다. vLLM `/metrics` 에서 셋만
보면 실제 상태가 나온다.

| 지표 | 신호 | 대응 |
|---|---|---|
| `num_requests_waiting` | > 0 지속 | 슬롯 부족 → `MAX_NUM_SEQS` 상향 검토 |
| `gpu_cache_usage_perc` | 90% 근처 지속 | KV pool 압박 → `GPU_MEMORY_UTILIZATION` 0.90 → 0.93 |
| prefix cache hit rate | 낮음 | TTFT 가 계속 비싸다 → 프롬프트 앞부분 고정 여부 점검 |

## 9. 증상 → 원인 → 레버

| 증상 | 어느 국면 | 진짜 원인 | 레버 |
|---|---|---|---|
| 첫 글자가 늦다 | prefill | 입력이 길다 | prefix cache 히트율, `MAX_NUM_BATCHED_TOKENS` ↑ |
| 첫 글자가 늦다 (입력은 짧은데) | 큐 | 슬롯 포화 | `MAX_NUM_SEQS` ↑ |
| 글자가 뚝뚝 나온다 | decode | 대역폭 | 가중치 FP8, 추측 디코딩 |
| 대화가 길어질수록 느려진다 | decode | KV 읽기가 커짐 | 컨텍스트 압축/compaction |
| 2턴째부터 다시 느리다 | prefill | 캐시 축출 | KV pool ↑ (`u` 0.90 → 0.93) |
| 기동이 KV 부족으로 실패 | - | pool < 1 시퀀스 | `u` ↑ **또는** `MAX_MODEL_LEN` ↓ (`MAX_NUM_SEQS` 는 무관) |

**멀티유저에서 가장 큰 단일 레버는 가중치 FP8 이다.** 51.5GB → ~26GB 가 되어
7.3절 "8명 200k" 가 104GB → 78GB 로 줄고 1인당 30 → 40 tok/s 가 된다.
`qwen3.8-27b.env` 에 "속도가 실제로 문제가 된 뒤에 판단" 이라고 적어둔 선택지인데,
**8명을 붙이는 것이 바로 그 상황**이다. 비용은 재다운로드 + 오프라인 청크 재업로드고
Qwen 공식 FP8 은 MLP 만 양자화라 품질 영향이 작다.
